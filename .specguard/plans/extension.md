# Implementation Plan: Implement SpecGuard VS Code Extension

> Generated by SpecGuard gap-analysis · 2026-06-29T01:47:28.927Z
> Spec: `specguard-core/extension`

## Summary

Build a VS Code / Cursor extension that surfaces SpecGuard spec coverage, pipeline status, and drift detection inside the IDE. The extension registers an activity-bar sidebar with a Coverage tree view, a singleton dashboard webview panel, and shells out to the `specguard` CLI for all business logic. The dashboard communicates with the extension host via VS Code's postMessage API, and the host translates commands into CLI invocations and pushes structured events back to the webview.

## Suggested Files

- `package.json` — Extension manifest: declares viewsContainers (activitybar), views (coverage tree), commands (specguard.openDashboard), activationEvents, and extension metadata
- `src/extension.ts` — Extension entry point: registers the sidebar tree view provider, the openDashboard command, and the drift background check (debounced 30s)
- `src/sidebar/CoverageTreeProvider.ts` — TreeDataProvider for the Coverage sidebar view — shows Coverage (per-app spec/test counts) and Outputs (Specs, Tests, Docs, Traceability) sections
- `src/dashboard/cli.ts` — Shared resolveCliPath helper (with .ts fallback for dev workspaces) and typed wrappers that shell out to the specguard CLI
- `src/dashboard/DashboardPanel.ts` — Singleton WebviewPanel manager: creates or reveals the panel, handles postMessage from webview, translates commands to CLI calls, and pushes coverage/matrix/findings/activity/workspace events back
- `src/dashboard/ViewModel.ts` — In-memory ViewModel holding lastRunInfo per pipeline card, drift state, and activity log; updated by CLI output and queried by the panel
- `src/dashboard/eventEmitter.ts` — Typed helpers to construct and send structured events (workspace, coverage, matrix, findings, activity, pipeline:lastRun) to the webview
- `webview/index.html` — Webview shell HTML loaded by DashboardPanel — bootstraps the React/vanilla JS bundle and sets up the VS Code API acquireVsCodeApi bridge
- `webview/src/App.tsx` — Root dashboard component: renders workspace info bar on all tabs, defaults to Overview tab, and routes to Overview / Pipelines / Matrix tab components
- `webview/src/tabs/OverviewTab.tsx` — Overview tab: workspace name, coverage summary, spec/test/doc counts, last drift/matrix status, recent activity feed, and Getting Started guide when no specs exist
- `webview/src/tabs/PipelinesTab.tsx` — Pipelines tab: Bootstrap section (reverse/import, hidden when specs exist), Main loop cards (generate→deps), Finalise section (heal/commit) — each card shows status chip, time-since, error tail, and Run button; import card is disabled with hint
- `webview/src/tabs/MatrixTab.tsx` — Matrix tab: renders traceability matrix from matrix event data; shows empty-state UI when no data is available

## Implementation Steps

1. 1. Scaffold the extension with `yo code` (TypeScript, no webpack initially); populate `package.json` with `viewsContainers.activitybar` entry (`specguard-sidebar` with SpecGuard icon), `views` entry for the coverage tree, and the `specguard.openDashboard` command under `contributes.commands`.
2. 2. Implement `src/dashboard/cli.ts`: write `resolveCliPath` (checks local `node_modules/.bin/specguard`, falls back to `specguard.ts` for dev workspaces), and typed async wrappers (`runCli(args, cwd)`) that spawn the CLI and return stdout/stderr.
3. 3. Implement `src/sidebar/CoverageTreeProvider.ts`: a `TreeDataProvider` that calls `specguard coverage --json` via `runCli`, parses output, and renders two top-level sections — **Coverage** (per-app spec/test counts) and **Outputs** (Specs, Tests, Docs counts, Traceability status). Register it in `extension.ts` with `vscode.window.registerTreeDataProvider('specguard-coverage', provider)`.
4. 4. Implement `src/dashboard/ViewModel.ts`: define the `ViewModel` class holding `lastRunInfo` map (pipeline id → {status, timestamp, errorTail}), `driftState`, and `activityLog`; expose mutator methods used by the panel and drift checker.
5. 5. Implement `src/dashboard/eventEmitter.ts`: typed factory functions for each event shape (`workspace`, `coverage`, `matrix`, `findings`, `activity`, `pipeline:lastRun`) that call `panel.webview.postMessage`.
6. 6. Implement `src/dashboard/DashboardPanel.ts`: singleton pattern (static `currentPanel`); on creation emit a `workspace` event (folder name, path, config status, app list); handle `onDidReceiveMessage` to dispatch CLI commands; after every pipeline run update `ViewModel.lastRunInfo` and emit `pipeline:lastRun`; implement `specguard reverse --all` by iterating apps from config.
7. 7. Register `specguard.openDashboard` in `src/extension.ts` to call `DashboardPanel.createOrShow()`; add a 30-second debounced drift background check that runs `specguard drift --json`, updates `ViewModel.driftState`, and only appends to the activity log when drift state changes.
8. 8. Build the webview UI: set up a `webview/` directory with a bundler (esbuild or webpack); create `index.html` as the panel shell; implement `App.tsx` with a tab bar defaulting to **Overview**, a persistent workspace info bar rendered on every tab, and routing to `OverviewTab`, `PipelinesTab`, and `MatrixTab`.
9. 9. Implement `OverviewTab.tsx` (workspace name, coverage summary, counts, last drift/matrix status, activity feed, Getting Started guide when spec count is 0), `PipelinesTab.tsx` (Bootstrap section hidden when specs exist; Main loop cards for generate/security/validate/docs/drift/matrix/quality/deps; Finalise section heal/commit; each card with status chip, time-since, error tail, Run button; `import` card disabled with terminal hint), and `MatrixTab.tsx` (matrix table or empty state).
10. 10. Wire end-to-end: verify the webview listens for all event types and updates state accordingly; add an `assets/specguard.svg` icon referenced in `package.json`; write a `launch.json` for Extension Development Host debugging and document manual test steps covering all 6 key scenarios.

## Testing Approach

For each of the 6 key scenarios, use the VS Code Extension Development Host (F5): (1) confirm the SpecGuard icon appears in the activity bar and the Coverage tree opens with Coverage + Outputs sections populated from CLI output; (2) open the dashboard and verify the workspace info bar shows folder name, path, config status, and app list on every tab; (3) navigate to Pipelines tab and confirm each main-loop card has a Run button that triggers the correct CLI command, updates the status chip, and emits `pipeline:lastRun`; (4) confirm the `import` card is rendered as disabled with a terminal hint and its Run button is non-interactive; (5) open the Matrix tab with no prior `specguard matrix` run and verify the empty-state UI is shown; (6) verify the Overview tab is the default tab on panel open and shows the Getting Started guide when no specs exist. Additionally, unit-test `resolveCliPath` (with and without the `.ts` fallback), `ViewModel.lastRunInfo` mutation, and the 30-second drift debounce logic (mock timers) using Jest or Mocha with the `@vscode/test-electron` harness.
